The problem

Every existing tool sees one layer. None connects them.

Validating mission software for a satellite constellation means reasoning about orbits, networks, and software execution at once. Today that takes three separate kinds of tool — and the seams between them are exactly where mission failures hide.

Models the sky

Orbital & topology simulators

Track movement, geometry, and when links appear and break.

Blind to the network traffic and the software riding on it.

Models the network

Network simulators

Move packets through realistic protocols, delay, and loss.

Blind to the execution logic of the real software sending them.

Runs the software

Containerized emulators

Execute real, unmodified software in isolated containers.

Blind to the chaotic, shifting space environment around it.

M2CATS closes the loop.

Real distributed software, running unmodified in Linux containers, connected through a live constellation network that moves, degrades, and reroutes exactly as orbit dictates. One platform where network behavior and software execution finally meet.

How it works

Real software above. Simulated space below.

Applications use ordinary sockets. Linux handles transport. The simulation controls everything between endpoints — routing, links, and channel conditions that change as satellites move.

Keep the software real. Make the conditions repeatable.

Each satellite endpoint runs in a Docker container with a real Linux TCP/IP stack — no simulation API, no simulation-aware application code. Your mission software runs exactly as it would in flight.

Linux TAP interfaces carry Ethernet frames into ns-3, where routing, link behavior, and channel conditions decide when — and whether — each packet arrives.

The difference

Other frameworks stop at orbital telemetry or network-level traffic. M2CATS runs your actual software on a standard Linux platform inside the simulated constellation — so you see software and network behavior as one system.
